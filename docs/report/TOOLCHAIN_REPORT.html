Overview

What runs where

SPK286 is CPU-only RTL, so every FPGA build in this report wraps it in one of two harnesses from this repository: an out-of-context timing build of the core alone, or the ZXTRES+ bring-up demo, the core on block RAM with an 80x25 VGA text screen and a self-checking x86 program. This page is a draft: the openXC7 demo passes its self-checks on a ZXTRES+ when uncompressed; the other figures are tool reports.

The bring-up demo as the Verilator simulation of boards/zxtres_plus captures it from the VGA outputs, 640 x 480 at 60 Hz, at the CPU clock of each build (run_sim.sh 400 33333 for the second): the 17 real-mode instruction tests, the BYTE sieve, the protected-mode tests and the hardware status line. The demo divides by the clock rounded to whole MHz, so at 33.333 MHz one sieve pass reads 32,823 us rather than 32,495. Uptime and frame count differ from the board's only because the simulation stops early.

i
Why openXC7 is slower

Yosys with ABC9 maps the core into more LUTs and deeper logic than Vivado (10,286 against 8,031 LUTs for the same demo), and nextpnr-xilinx lacks Vivado's physical optimization: no phys_opt, register replication or aggressive rerouting. The gap is about 30 % on the same device. The openXC7 demo defaults to 33.333 MHz, below the 37–42 MHz the router reports, because nextpnr's delay model is an estimate. The margin is a precaution, unrelated to the boot failure, which came from the compressed bitstream. No openXC7 build above 33.333 MHz has been tried on a board yet; the Vivado demo meets 50 MHz in timing reports.

Where the microcode ROM goes

Each tool maps the synchronous microcode ROM its own way: Quartus to 2 M10K blocks, Vivado to LUTs (a 1024 x 13 ROM after optimization, in the harness and in the demo alike) and Yosys to a block RAM. Neither the core nor the demo uses a DSP block: multiply and divide are iterative.

For the core alone, analysis and synthesis take under four minutes; the Fitter dominates and used 1.3 processors on average, with the timing analysis on three.

Vivado

Synthesis is the slowest step of the demo build (5 min 07 s); placement and routing take a little over two minutes and spread over several cores.

openXC7

Yosys synthesizes the demo in about 90 s; nextpnr-xilinx takes most of the run. The flow adds the bitstream patch and a read-back check (section 06).

06

Bitstreams

From bitstream to a loadable core

A ZXTRES+ core (.ZX3) is the configuration data of the .bit file without its header, padded to a multiple of 16 KiB. The ZXTRES+ cores are built with SPI_BUSWIDTH 4, SPI_32BIT_ADDR YES and compression. The openXC7 core is not compressed, and the board loads it that way. The Quartus harness is timing-only and produces no core to load.

Compressing a prjxray bitstream: it does not boot

Vivado writes each distinct frame once: frames with the same contents are loaded into the frame buffer and copied to their other addresses with MFWR (eight NOOPs after each in block RAM content), and the rest go out in runs within a column, each followed by one pad frame. CTL1 bit 12 is set around the frame writes. compress_bitstream.py does the same with the frames of the prjxray bitstream, after checking every frame of the fasm2frames output at its address.

prjxray's bitread does not follow multiple frame writes, so decode_frames.py models the configuration logic: the frame buffer, WCFG, MFW and the frame address order of the part. On Vivado's own compressed and uncompressed bitstreams of the same routed demo it decodes identical frames at all 9,448 addresses; on the openXC7 build, the compressed core writes the same frames as the uncompressed one.

The board disagrees with that model. The openXC7 core compressed this way showed the screen but the CPU never ran (POST 00); uncompressed, the same design passes the 22 checks. A Vivado-routed copy of the demo converted through the same tools boots uncompressed and gives a black screen compressed. The cause is not known, so compress_bitstream.py stays optional (COMPRESS=1) and off by default, and the frame check alone cannot certify a compressed core.

!
Confirmed on a board

The uncompressed openXC7 core, with Vivado's flash read settings in its configuration header, boots on a ZXTRES+ and passes the 22 checks; the compressed one does not.

07

Verification

What each flow is checked against

RTL simulation

  • Verilator runs the demo system with the VGA testbench: 22 / 22 checks, 1,899 primes, 1,083,160 cycles a pass, no sync errors.
  • The same simulation backs every flow; the core's own regression and SingleStepTests coverage are in the core datasheet.

Static timing

  • Quartus and Vivado: signoff reports, all constraints met in the builds above.
  • openXC7: nextpnr's estimate; the build fails when a clock misses its constraint.

openXC7 extras

  • Read-back: the prjxray bitstream decoded with prjxray holds exactly the features nextpnr placed (0 missing, 0 unexpected); a three-byte corruption fails it.
  • Frame check: the final core writes the same frames at all 9,448 addresses as the prjxray bitstream. It cannot certify a compressed core: that one decodes identically and still does not start on the board.
  • Netlist simulation: the Yosys netlist against the RTL. It matches the RTL: the 27 POST codes at the same nanoseconds and both VGA frames pixel-identical, after about 80 minutes of simulation (the RTL takes two).
i
A gap in the open cell library

Yosys's simulation library declares RAMB18E1 and RAMB36E1 without any behaviour, so a netlist simulated with it reads zeros from every block RAM and the CPU faults after reset. Bisecting the flow showed the netlist matching the RTL up to memory mapping. The board directory carries a behavioural model of both primitives, limited to the configurations Yosys emits and stopping on any other.
